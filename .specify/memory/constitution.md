# Конституция проекта «Пасека» (Beekeeping Management System)

Обязательные правила для всех, кто работает над проектом: людей и ИИ-агентов.
Полное техническое задание: [`docs/requirements.md`](../../docs/requirements.md).
Практические указания для агентов: [`CLAUDE.md`](../../CLAUDE.md).

## Core Principles

### I. История неприкосновенна

Система обязана отвечать на вопрос «что происходило с каждым ульем, семьёй и маткой за весь год».

- Ульи, семьи, матки, пасеки и любые записи учёта ЗАПРЕЩЕНО удалять физически. При выбытии
  меняется статус, ставится дата окончания и указывается причина.
- Каждое важное изменение ОБЯЗАТЕЛЬНО пишется в `audit_logs`: пользователь, дата и время,
  сущность, действие, старое и новое значение, комментарий.
- Замена матки, смена семьи, перемещение, разделение, объединение, продажа и гибель ОБЯЗАНЫ
  сохранять связь со старым состоянием (отдельные таблицы периодов: `queen_assignments`,
  `bee_families` с `start_date`/`end_date`, `hive_movements`, `hive_splits`, `hive_merges`).
- UUID улья постоянен: на него указывает QR-код. Смена номера, матки, семьи или пасеки
  НЕ МОЖЕТ менять UUID.

Обоснование: ценность продукта — в непрерывной истории; потерянную историю нельзя восстановить.

### II. Безопасность по умолчанию (NON-NEGOTIABLE)

- Telegram user ID, пришедшему от клиента, ЗАПРЕЩЕНО доверять без проверки подписи `initData`
  (HMAC-SHA256 с ключом бота) и срока её действия.
- Каждый endpoint, кроме `/api/health` и endpoints входа, ОБЯЗАН требовать JWT и проверять
  роль (ADMIN, BEEKEEPER, ASSISTANT, VIEWER). Роль читается из базы при каждом запросе.
- Endpoints входа без JWT проверяют личность своими средствами: `/api/auth/telegram` — подпись
  `initData`; вход в приложение на телефоне вне Telegram — одноразовый код (5 минут), который
  пользователь подтверждает в боте, и секрет устройства, запросившего код; подтверждение от бота —
  HMAC токена бота; сессия устройства — случайный токен, хранимый только в виде хэша, отзываемый
  и истекающий без использования.
- Секреты хранятся только в `.env`. В Git ЗАПРЕЩЕНО коммитить токены, пароли и `.env`.
- Ввод проверяется на сервере (Pydantic и ограничения БД); SQL пишется только через ORM или
  параметризованные запросы; production работает только по HTTPS с rate limiting.

Обоснование: в системе финансовые и производственные данные пасеки, а Mini App доступен из интернета.

### III. Данные — в реляционной модели PostgreSQL

- Production-база — только PostgreSQL. SQLite ЗАПРЕЩЁН.
- Бизнес-данные хранятся в нормальных столбцах с типами и ограничениями. JSON допускается только
  для снимков в журнале изменений.
- Основные сущности используют UUID-ключи.
- Любое изменение схемы делается только миграцией Alembic; `alembic check` должен показывать
  отсутствие расхождений.
- Инварианты домена закрепляются в БД: одна активная матка на улей, одна активная семья на улей,
  неотрицательные вес, количество рамок и суммы.
- Производные значения не хранятся, а вычисляются: возраст матки из даты рождения,
  `total_value = weight_kg × price_per_kg`, мёд за период, прибыль.

Обоснование: целостность данных обеспечивает база, а не только код приложения.

### IV. Mobile-first для пасеки

- Интерфейс проектируется для телефона внутри Telegram WebView и как приложение на главном экране (PWA) (iPhone и Android): карточки,
  нижняя навигация, крупные кнопки, быстрые действия, минимум текста.
- Широкие таблицы на маленьком экране ЗАПРЕЩЕНЫ.
- Все ошибки показываются пользователю понятным русским языком; сервер возвращает
  `{detail, errors:[{field, message}]}`.
- Главный сценарий ОБЯЗАН работать за минимум касаний: сканировать QR → паспорт улья →
  осмотр → сохранить.

Обоснование: приложением пользуются в перчатках, на солнце, с плохой связью.

### V. Проверено тестами, работает по-настоящему

- Каждый этап завершается зелёными тестами backend (pytest на реальной PostgreSQL с миграциями)
  и frontend (Vitest), а также успешной сборкой frontend.
- Новая бизнес-логика сопровождается тестами: правила домена, права доступа, валидация.
- ЗАПРЕЩЕНЫ заглушки, mock-функции вместо реальной логики и `TODO` вместо работающего
  функционала. Ещё не реализованный раздел явно помечается в интерфейсе номером этапа.
- Обязательные сценарии из ТЗ (раздел 38) покрываются тестами по мере появления.

Обоснование: пчеловод должен доверять цифрам — мёду, возрасту маток, прибыли.

## Технологические ограничения

- Frontend: React, TypeScript, Vite, React Router, TanStack Query, Telegram Mini Apps SDK.
- Backend: Python 3.12+, FastAPI, SQLAlchemy 2, Alembic, Pydantic, PostgreSQL, REST и OpenAPI.
- Слои backend: `routers` (HTTP) → `services` (правила, аудит) → `repositories` (запросы) →
  `models`.
- Бот: aiogram. Развёртывание: Docker Compose (frontend, backend, postgres, bot, nginx), HTTPS
  через nginx.
- Монорепозиторий `backend/`, `frontend/`, `bot/`. Архитектура меняется только при
  обоснованной необходимости и с поправкой к этой конституции, если затронуты принципы.

## Процесс разработки

- Работа идёт по 10 этапам из ТЗ (раздел 40). Следующий этап начинается только после проверки
  предыдущего.
- Для нового этапа или крупной функции используется цикл Spec Kit: `/speckit-specify` →
  (`/speckit-clarify`) → `/speckit-plan` → `/speckit-tasks` → (`/speckit-analyze`) →
  `/speckit-implement`. Спецификации хранятся в `specs/NNN-название/`.
- Изменения делаются небольшими логическими коммитами; рабочий код не удаляется без
  необходимости.
- После каждого этапа сообщается: что сделано, какие файлы изменены, как проверить, какие тесты
  прошли.
- `seed`-скрипт (`backend/app/utils/seed.py`) расширяется на каждом этапе, чтобы демо-данные
  покрывали новые модули.

## Governance

- Эта конституция имеет приоритет над остальными практиками проекта. При конфликте `CLAUDE.md`,
  README или спецификации приводятся в соответствие с ней.
- Поправки вносятся через `/speckit-constitution` с отчётом о влиянии, обновлением версии и
  коммитом `docs: amend constitution to vX.Y.Z (...)`.
- Версионирование: MAJOR — удаление или переопределение принципа; MINOR — новый принцип или
  раздел; PATCH — уточнения формулировок.
- Каждый план (`/speckit-plan`) и ревью проверяют соответствие принципам I–V. Отступление
  допускается только с письменным обоснованием в плане.
